# Diagnostic Labs (rewrite)

Modern rewrite of the legacy WPF/.NET Framework app. The database schema and the app's concept are unchanged; the code is new.

## Layout

| Project | Role |
|---|---|
| `src/DiagnosticLabs.Domain` | Entities and rules. No EF, no UI. |
| `src/DiagnosticLabs.Application` | Use-case services, abstractions (`IAppDbContext`, `ICurrentUser`, `IPasswordHasher`), `Result<T>`. |
| `src/DiagnosticLabs.Infrastructure` | EF Core 10 (SQL Server), entity configurations, audit interceptor, PBKDF2 hasher. |
| `src/DiagnosticLabs.Wpf` | WPF shell, CommunityToolkit.Mvvm, Generic Host DI, Serilog. |
| `tests/DiagnosticLabs.Application.Tests` | xUnit tests. |
| `scaffold-draft/` | Raw scaffold of the legacy schema. Reference only, not compiled. |
| `db/schema.sql` | Idempotent SQL script generated from the EF migrations (`dotnet ef migrations script --idempotent`). |
| `docs/AUDIT.md` | Audit of the legacy app and the migration plan. |

## Run

Set your SQL Server in `src/DiagnosticLabs.Wpf/appsettings.Local.json` (gitignored, per machine):

```json
{ "ConnectionStrings": { "DiagnosticLabs": "Server=.;Database=DiagnosticLabsV2;Trusted_Connection=True;TrustServerCertificate=True" } }
```

```bash
dotnet ef database update --project src/DiagnosticLabs.Infrastructure   # creates/updates the new database
dotnet run --project src/DiagnosticLabs.Wpf
dotnet test
```

The new app uses its own database (`DiagnosticLabsV2`), never the legacy `DiagnosticLabsDB`. Set `DL_MIGRATION_CONNECTION` if `dotnet ef` should target a different server.

Logs are written to `%LOCALAPPDATA%\DiagnosticLabs\logs`.

## Passwords

New hashes are PBKDF2-SHA256 (`v1$iterations$salt$hash`). Users still holding the legacy unsalted SHA-1 hash can sign in once and are upgraded automatically.

## Migrating data from the legacy database

The legacy `DiagnosticLabsDB` is only ever read. To copy its data into a freshly migrated, empty new database (PowerShell):

```powershell
dotnet ef database update --project src/DiagnosticLabs.Infrastructure
sqlcmd -S <server> -d DiagnosticLabsV2 -E -C -I -b -i db\migrate-from-legacy.sql -v Legacy=DiagnosticLabsDB 'LegacyTimeZone="Singapore Standard Time"'
sqlcmd -S <server> -d DiagnosticLabsV2 -E -C -I -b -W -i db\verify-migration.sql -v Legacy=DiagnosticLabsDB
```

`LegacyTimeZone` is the Windows time zone the legacy app's local timestamps were recorded in (they are stored as UTC in the new database). The script runs in one transaction, refuses to run on a non-empty target, and lists any lab rows it could not migrate. `db/migrate-from-legacy.sql` and `db/verify-migration.sql` are generated by `tools/Generate-LegacyMigration.ps1`; re-run that if the model changes.

## Migration status

| Module | Status |
|---|---|
| Sign in, permissions, navigation menu | Done |
| Patients | Done (paged search, create/edit/soft-delete, concurrency check, audit log) |
| Companies, Departments, Services, Packages, Discounts | Done (shared list + editor screen; delete switches a row off, "Show inactive" brings it back) |
| Items, Item Locations | Built and tested, but hidden: the legacy `Modules` table has them switched off (`IsActive = 0`, ids 21 and 22). Set `IsActive = 1` to show them in the menu |
| Patient Registrations, Payments, Lab Results, Reports, Settings | Shown in the menu as "not migrated yet" |

A new maintenance screen is: a service deriving from `CrudService`/`ReferenceCrudService` (Application), a view model deriving from `CrudViewModel` (Wpf), a `DataTemplate` in `Views/CrudTemplates.xaml` that fills the shared `CrudLayout`, and one line in `MainViewModel.Pages`. `Management/DiscountService` and `MasterDetailViewModels.cs` show the pattern with child rows.
